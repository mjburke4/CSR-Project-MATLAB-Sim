# Tranche 23: receiver pressure and ACK/DACK replay

T23 tests how receiver node 8 generates ACK/DACK feedback and maintains relay
custody when local and relayed traffic share its downstream path. It follows
T22's accepted adaptive-window test. The simulator source remains unchanged.

Copy your **accepted T22 installation** to a short path such as `C:\csr23`.
Extract every file from `t23up.zip` over that copy, replacing files if prompted.
Run from that folder in MATLAB:

```matlab
clear functions
report = run_tranche23_validation;
```

This runs **79 focused tests and seven short controlled cases**, recording
123 settled state checkpoints and the feedback actually emitted. It does not
run the 6,000-second campus simulation. PHY/ECC, continuous timing and the
actual-transmission retry policy remain unchanged.

Upload the **`t23.zip`** whose full path MATLAB prints. Each invocation writes
a fresh folder beneath `results/t23/`. Return the ZIP even if a test fails;
the runner preserves completed tests and attempts to preserve the main replay.

Native execution revealed a specific behavior to compare: retrying a packet
that was DACKed can create another NWK custody owner. MATLAB's existing
application-duplicate suppression may prevent that extra owner. This is a
hypothesis about the MATLAB result until your run confirms it, and it is not
yet an explanation of the campus performance gap.

A completed run can report `completed-differences-review-required`. That is a
valid diagnostic outcome when focused tests and evidence checks pass; exact
native comparison differences are retained for review. A failed common
behavioral assertion or an incomplete run still reports failure and must be
reviewed. No simulator change or parity acceptance is implied by either result.

The ±10% working goal remains for campus performance. These controlled cases
compare exact integer states and feedback bitmaps, with a 1 ns time tolerance.
They are decoded-packet/callback tests, not real-PHY or security-ingress tests.
