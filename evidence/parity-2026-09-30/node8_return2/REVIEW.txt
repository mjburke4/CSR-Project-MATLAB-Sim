CONFIRMED CAUSE
At 694.262813632 seconds, node 4 accepts source 7 application attempt 2873 from
node 2 (ingress HOP sequence 162). Both models increase source-7 NSDP from 25 to
26. At 694.821813632 seconds, another copy arrives. Both HOP implementations
classify the DACK-marked retry as a first reception for this pass and generate
DACK feedback. Native NWK accepts a second relay queue occurrence, increasing
NSDP from 26 to 27. MATLAB returns success without enqueueing it, keeping 26.

The active MATLAB class is ac.DiscoveryMembershipNwk, constructed by
ac.TerminalSimulation. receiveData's Seen(appKey) guard suppresses the repeated
relay application before it reaches enqueueApplication. The enqueue guard and
pending/submission/release lookup also use application identity rather than a
distinct local custody occurrence. The corresponding production NWK class has
the same design constraints. Removing only the Seen guard is insufficient.

Native csr-hop-layer.h explicitly treats DACK-marked retries as eligible for
another NWK delivery; csr-nwk-layer.h increments NSDP and queues each accepted
relay occurrence. This establishes a mismatch to the pinned ns-3 behavior. It
does not independently prove whether that legacy behavior is the desired design
for a different protocol or system.

RECOMMENDED REPAIR AND NEXT VALIDATION
Make each accepted relay custody occurrence distinct while preserving the
original end-to-end application identity for unique delivery accounting.
Update the active candidate and its production counterpart consistently.
Keep final-destination reporting deduplication separate from relay queue policy.

One focused bundle should cover these boundaries together:
1. An ACK-marked duplicate is suppressed at HOP; a DACK-marked retry accepted by
   HOP creates another relay queue/NSDP occurrence, as in the captured case.
2. Both occurrences coexist, preserve FIFO order, receive distinct outgoing HOP
   ownership and release custody exactly once each. Completion/expiration of one
   must not remove its sibling or double-release capacity.
3. End-to-end accounting still counts the application once, including late-copy
   delivery and orphan feedback behavior.
4. Rerun the same seed132 0–1200 common-input replay with unchanged strict context
   and timestamp gates, specifically checking 694.821813632, 894.464292500 and
   895.115 seconds. The verified native fixture already exists.

Do not run another unchanged long autonomous simulation first. After the repair
passes this bounded replay, assess its effect on the original 6,000-second
source-by-source counts and latency with unfinished traffic and source mix.
The current full-run +/-20-percent milestone remains unmet; its previously
measured source-weighted latency gap (+40.7 percent) is not re-estimated here.
This review identifies a specific cause of replay divergence, not the full
explanation or expected size of the autonomous latency gap.
