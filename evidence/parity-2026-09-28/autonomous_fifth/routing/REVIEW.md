## Causal boundary

The direct MATLAB control-reception log contains only KEY_REQUEST and KEY_UPDATE from node 3 before admission. There is no received DISCOVER, NEIGHBOR_CHECK or ROUTING from node 3. Radio observations save metrics but do not create route candidates. The ACK completion invokes `MessageFlagNwk.neighborChanged(3,true)`.

That callback calls `Routes.setNeighbor`. The function both admits the peer and allocates a direct candidate when none exists. The new candidate is valid with capability zero. Its selection changes from absent to present, so `finish` marks destination 3 changed; `changeRecord` serializes capability-zero selection as DELETE. `processRoutes` sends the pending snapshot first, then broadcasts the changed-route record to active peers `[3,5]`. These two controls are directly visible in ordered observations 13087 and 13095.

Native `TryMakeNeighborActive` instead creates the **logical destination**, sets neighbor admission state, releases existing valid deferred candidates for that destination, and compares selected state before/after. It does not allocate or revalidate a route candidate. With no candidate to node 3, both selected states are absent and the callback queues only the snapshot. Native's first actual candidate to node 3 is later created by `ProcessHello`.

The extra DELETE is not an INFO/population update. Removing or suppressing all DELETEs would be incorrect: when an already observed capability-zero direct candidate becomes selectable at admission, DELETE is the expected changed-route operation.

## Isolated H change

`+ac/AdmissionRoutes.m` adds `admitNeighbor(peer,linkCost,now)` to an isolated copy of the issued Routes class. H binds only the active-neighbor callback to that method. `refreshLink` retains the original `setNeighbor` path, so subsequent observed HELLO processing can still create or update direct routes.

The admission method preserves these native boundaries:

- It records logical destination creation even when no candidate exists. Native explicitly calls `NoteDestinationCreated` during admission; removing this side effect would change later destination ordering.
- It activates peer admission and releases only valid deferred candidates for `DestinationId == peer` with usable next hops.
- It does not allocate, revalidate, reprice or retimestamp a direct candidate. Existing peer link-cost bookkeeping is retained; a new peer record receives the supplied initial value.
- It compares the selected state before and after admission, preserving legitimate UPDATE and DELETE records. Repeated admission of an already active peer is a no-op.

This scope concerns the admission operation itself. Native `NoteNeighborCheckSuccess` separately reactivates stale direct candidates and recomputes valid routes before admission; the current captured event has `stale=0->0` and no existing candidate. The change does not establish parity for every stale-neighbor recovery path.

`build_admission_routes.py` records an exactly reversible transformation: removing the new method and reversing the class, constructor and 25 static self-reference renames reproduces the issued Routes file byte-for-byte. No model file changes are required. Builder integration uses `AdmissionNwk` and `AdmissionSimulation`; G remains population-only, while H adds this route-admission change.

The offline audit passed: two MATLAB controls decoded; the extra record is exactly DELETE3; the snapshot matches the native transmitted section byte-for-byte; only one native routing control is queued at the admission timestamp; and the first native direct candidate appears at 18.724108077 seconds.

The native agent's public-API component probe independently passed three route cases, using real key exchange and ACK callbacks without a network or PHY:

1. Unobserved-peer admission leaves no selected candidate or changed-route control; a later HELLO creates the route and emits DELETE.
2. A previously observed capability-zero candidate becomes selectable and emits DELETE on admission.
3. A previously observed candidate with a source-owned capability-one self UPDATE becomes selectable and emits UPDATE.

The MATLAB kit contains eight public-API preflight checks, including a negative control that reproduces `00000004000101000003`, later observation, legitimate zero/capable candidates, candidate-field preservation, transit deferral, invalid cached-route preservation and logical destination order. **Those MATLAB preflights have not been executed here.** Full G/H continuation is also pending; this report does not claim improved throughput, latency or attainment of the 15% parity target.
